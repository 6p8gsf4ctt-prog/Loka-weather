LOKA V24 — BLOC 12.9
======================

OBJECTIF
--------
Auditer exhaustivement les 24 scènes officielles avant d'autoriser les
étapes de rollback réel et d'audit final.

Le Bloc 12.9 vérifie chaque élément de la chaîne :

registre
→ ID
→ key
→ label
→ family
→ masterFileName
→ lookup ID/key
→ payload V24
→ éditorial natif
→ master physique via Cloudflare ASSETS

Aucune scène n'est injectée dans la production.

MIGRATION D1 OBLIGATOIRE
------------------------
Appliquer :
migrations/0009_scene_catalog_audit.sql

Elle crée :
scene_catalog_audit

La table est append-only :
UPDATE et DELETE interdits.

FICHIERS À AJOUTER
------------------
- migrations/0009_scene_catalog_audit.sql
- src/engine/sceneCatalogAudit.ts
- src/storage/sceneCatalogAudit.ts

FICHIERS À REMPLACER
--------------------
- src/engine/engineMode.ts
- src/engine/engineRuntime.ts
- src/pipeline.ts
- src/index.ts
- src/ui/dashboard.ts

Le ZIP inclut aussi les dépendances nécessaires du Bloc 12.8.

CE QUI EST CONTRÔLÉ AU NIVEAU DU REGISTRE
-----------------------------------------
- exactement 24 scènes
- IDs exactement 01 → 24 dans l'ordre
- 24 IDs uniques
- 24 keys uniques
- 24 noms de master uniques
- key / label / family / description / master non vides

Pour chaque scène :
- getScene24ById(id) retourne exactement la définition du registre
- getScene24ByKey(key) retourne exactement la même définition
- masterFileName doit être exactement :

  NN_KEY.png

Exemple :
09_COUVERT.png
24_PLUIE_PLUS_VENT.png

AUDIT DU PAYLOAD PUBLIC
-----------------------
Pour chacune des 24 scènes, LOKA construit un forecast CLONÉ en mémoire et
force uniquement le diagnostic scene24 du clone.

Puis buildV24PublicPayloadPreview() doit réussir.

Le test vérifie que le payload produit exactement :
- le bon ID
- la bonne key
- le bon label
- la bonne family
- le bon masterFileName
- la bonne URL /masters24/...

Cela teste donc le même chemin registry → publicPreview utilisé par V24.

AUDIT DES 24 ÉDITORIAUX
-----------------------
Le même build déclenche buildV24NativeEditorial() pour CHAQUE scène.

Le Bloc 12.9 vérifie :
- source = v24_native_v1
- subtitle non vide
- mainVerdict non vide
- rainVerdict non vide
- 2 à 3 summaryLines
- aucune ligne vide
- mainVerdict = subtitle
- 24 subtitles uniques

Le test utilise une copie du DayProfile réel et active, sur cette copie,
les branches correspondant à la scène :
- dégradation
- amélioration
- pluie
- vent
- orage
- brouillard

Cela permet de tester aussi les phrases conditionnelles sans modifier le
forecast officiel.

AUDIT DES 24 MASTERS PHYSIQUES
-------------------------------
Chaque master déclaré est réellement demandé via le binding Cloudflare :

ASSETS -> ./public

Pour chacune des 24 images :
- binding ASSETS disponible
- requête réussie
- HTTP OK
- Content-Type image/*
- fichier accessible à /masters24/<masterFileName>

Donc le test ne se contente pas de regarder le nom du fichier dans le code.

SÉCURITÉ
--------
Le Bloc 12.9 ne fait jamais :
- saveForecast()
- rollbackToLegacy()
- activation V24
- modification engine_control
- modification readiness
- modification d'un master

Seule écriture :
scene_catalog_audit

Cette ligne d'audit contient le détail des 24 scènes.

PENDING
-------
PENDING ne devrait apparaître que si ASSETS n'est pas disponible dans
l'environnement où le test est exécuté.

Sur le Worker Cloudflare normal, avec le binding ASSETS, le résultat attendu
est PASS ou FAIL, pas PENDING.

FAIL
----
Un seul FAIL suffit pour bloquer la validation du Bloc 12.9.

Exemples :
- master manquant
- mauvais nom de fichier
- key dupliquée
- ID hors séquence
- éditorial absent
- payload impossible à construire
- image non accessible

On ne passe pas au Bloc 12.10 tant qu'un FAIL reste présent.

7. Vérifier PASS 24/24.

ÉTAT DU PROJET
--------------
Le registre actuellement présent contient bien les 24 IDs officiels 01-24,
et publicPreview construit les URLs à partir de /masters24/<masterFileName>.

Le Bloc 12.9 transforme maintenant ces conventions en assertions exécutables
et auditables dans le Worker.
