LOKA V24 — BLOC 12.6
======================

OBJECTIF
--------
Garantir qu'une génération officielle est IDENTIQUE sur les quatre surfaces :

- /api/latest
- /api/decision
- /
- /instagram

Le contrôle porte sur :
- generatedAt
- moteur effectif
- scène
- fingerprint SHA-256 du produit public

AUCUNE surface ne doit pouvoir dériver silencieusement d'une autre.

MIGRATION D1 OBLIGATOIRE
------------------------
Appliquer :
migrations/0006_publication_coherence.sql

Elle crée deux tables append-only :

1. publication_generation_audit
   Une preuve immuable par génération réellement publiée.

2. publication_surface_audit
   Le résultat des contrôles réels des quatre surfaces.

MANIFEST CANONIQUE
------------------
Chaque génération 12.6 reçoit :

diagnostics.publicationManifest

Il contient notamment :
- city/date/generatedAt
- effectiveEngine
- scène
- master V24 si applicable
- score/confiance
- éditorial
- températures
- hourly
- état garde-fou/fallback
- surfaceContractVersion

LOKA calcule un SHA-256 déterministe de ce contenu :

fingerprintSha256

Le même fingerprint doit apparaître partout.

ÉCRITURE D1
-----------
Avant publication :
- le manifest est attaché au forecast
- le backup Legacy persistant reçoit lui aussi un manifest

Après saveForecast :
- LOKA relit la génération
- vérifie le moteur
- RECALCULE le fingerprint
- compare au manifest stocké

Puis une ligne est ajoutée à :
publication_generation_audit

IMPORTANT :
pour une génération V24, cette preuve d'audit est OBLIGATOIRE.

Si l'audit V24 ne peut pas être enregistré :
→ V24 est abandonné
→ récupération Legacy
→ aucune génération V24 non traçable n'est conservée.

Pour Legacy, une panne d'audit ne coupe pas la météo, mais la génération sera
signalée PARTIAL et le contrôle 12.6 ne pourra pas être validé.

HEADERS PUBLICS
---------------
Les 4 surfaces officielles renvoient désormais :

x-loka-publication-version
x-loka-generated-at
x-loka-engine
x-loka-scene
x-loka-publication-fingerprint
x-loka-surface

Exemple :
x-loka-publication-version: 12.6.0
x-loka-engine: LEGACY
x-loka-scene: NUAGES
x-loka-publication-fingerprint: ...

Ces headers proviennent TOUS du même publicationManifest.

CONTRÔLE MOBILE RÉEL
--------------------
Nouveau bouton Admin :

"Contrôler cohérence 12.6"

Ce bouton ne simule pas les surfaces.

Depuis Safari/Chrome sur ton téléphone, il appelle réellement :

1. /api/latest
2. /api/decision
3. /
4. /instagram

Il lit leurs headers LOKA et vérifie que les quatre réponses ont exactement :

- HTTP 2xx
- version 12.6.0
- même generatedAt
- même moteur
- même scène
- même fingerprint

Le résultat est ensuite envoyé au serveur qui le REVALIDE par rapport au
manifest officiel courant.

Puis le résultat PASS/FAIL est écrit dans :
publication_surface_audit

Ce test ne modifie :
- ni forecast
- ni engine_control
- ni autorisation V24

Il ajoute uniquement une ligne d'audit append-only.

FALLBACKS
---------
Le Bloc 12.5 reste intégralement en place.

En plus, une génération V24 n'est plus servie si son publicationManifest est
absent, invalide ou si son fingerprint ne correspond plus au contenu réel.

Dans ce cas :
→ backup Legacy persistant
→ sinon backup Legacy inline
→ sinon 503 sécurisé

INSTALLATION MOBILE
-------------------
1. Appliquer migrations/0006_publication_coherence.sql dans D1.
2. Ajouter/remplacer les fichiers du ZIP.
3. Déployer.
4. Générer UNE nouvelle météo.
5. Admin -> Contrôler le moteur.
6. Tester les fallbacks 12.5.
7. Contrôler cohérence 12.6.

-----------------------

publication_generation_audit : VERIFIED

CAS PRE-12.6
------------
Juste après déploiement, avant la première nouvelle génération, l'ancien
forecast peut ne pas avoir publicationManifest.

C'est normal.

Il faut générer UNE nouvelle météo avant de valider le Bloc 12.6.
