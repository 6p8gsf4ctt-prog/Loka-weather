LOKA V24 — BLOC 12.5
======================

OBJECTIF
--------
Durcir le mécanisme de publication/fallback pour qu'une défaillance V24 ne
puisse ni publier un produit incomplet, ni écraser le dernier produit sûr.

Ce bloc ne change PAS les critères de readiness.
Avec NOT_READY, la production reste LEGACY.

NIVEAU 1 — MASTER V24 RÉELLEMENT VÉRIFIÉ
-----------------------------------------
Le Worker possède déjà un binding Cloudflare :
ASSETS -> ./public

Le Bloc 12.5 l'utilise maintenant.

Avant toute génération V24 officielle :
- le master choisi est demandé via env.ASSETS
- HTTP doit réussir
- Content-Type doit être image/*
- sinon activationGuard = BLOCKED
- génération = LEGACY

Le master est également REVÉRIFIÉ à chaque requête publique V24.

Donc la suppression accidentelle d'un master après génération déclenche
immédiatement le fallback Legacy.

NIVEAU 2 — BACKUP LEGACY PERSISTANT
-----------------------------------
Avant de publier une génération V24 :

1. LOKA vérifie le snapshot Legacy inline.
2. Il reconstruit le forecast Legacy complet.
3. Il l'enregistre dans public_forecast_backup.
4. Il calcule un SHA-256 du JSON.

Si cette sauvegarde échoue :
V24 N'EST PAS PUBLIÉ.
La génération est forcée en Legacy.

Le backup est aussi rafraîchi pendant les générations Legacy normales.

NIVEAU 3 — ÉCRITURE D1 SÉCURISÉE
---------------------------------
La nouvelle publication suit :

prepareSafePublication()
→ backup Legacy
→ validation JSON
→ commitSafePublication()
→ écriture forecasts
→ relecture D1
→ vérification generatedAt + moteur effectif

Cas V24 :
- write échoue -> tentative récupération Legacy
- relecture incohérente -> réécriture Legacy
- récupération Legacy échoue aussi -> exception
  et le précédent forecast public reste l'unique produit de confiance

LOKA ne doit jamais répondre que la nouvelle génération est publiée si
l'écriture n'a pas été vérifiée.

NIVEAU 4 — FALLBACK À LA REQUÊTE
---------------------------------
Les 4 surfaces officielles passent par le même resolver sécurisé :

/api/latest
/api/decision
/
/instagram

Pour servir V24 il faut maintenant :

- produit stocké V24 valide
- guard PASS
- backup Legacy persistant lisible + checksum valide
- master officiel toujours disponible

Si une vérification échoue :
→ backup Legacy persistant

Si D1 backup est indisponible :
→ snapshot Legacy inline

Si aucun fallback sûr n'existe :
→ LOKA REFUSE de servir le V24
→ HTTP 503 "Prévision temporairement indisponible"

C'est volontairement plus sûr que de montrer une donnée incohérente.

NIVEAU 5 — AUDIT FALLBACK
-------------------------
Les incidents de publication sont enregistrés dans :
publication_fallback_audit

Stages :
PREFLIGHT
BACKUP
WRITE
VERIFY
RECOVERY

L'audit ne participe jamais au fonctionnement du fallback.
Une panne de la table d'audit ne peut pas empêcher un rollback/fallback.

NIVEAU 6 — SELF-TEST MOBILE
----------------------------
Nouveau bouton Admin :
"Tester les fallbacks 12.5"

Route privée :
GET /api/admin/engine/fallback-self-test?city=tarnos

Le test est LECTURE SEULE et ne modifie jamais la production.

Il contrôle notamment :
- master V24 courant accessible
- faux master absent correctement détecté
- payload V24 corrompu refusé
- guard BLOCKED => Legacy
- restauration du snapshot Legacy
- erreur JSON détectée avant D1
- backup Legacy persistant + checksum
- surface publique courante résolue sans danger

INSTALLATION MOBILE
