LOKA V24 — BLOC 12.8
======================

OBJECTIF
--------
Tester les pannes et cas dégradés AVANT le GO LIVE, sans casser ni modifier
la production réelle.

Le Bloc 12.8 introduit un laboratoire de panne contrôlé.

AUCUNE panne n'est injectée dans :
- forecasts
- engine_control
- readiness
- autorisation V24
- publication officielle

Les scénarios sont exécutés sur des clones mémoire et sur la même politique
de récupération utilisée par le code de production.

MIGRATION D1 OBLIGATOIRE
------------------------
Appliquer :
migrations/0008_fault_injection_audit.sql

Elle crée :
fault_injection_audit

Cette table est append-only.

Chaque exécution du laboratoire y écrit une seule preuve :
- PASS / FAIL / PENDING
- nombre de scénarios
- résultat complet
- production_mutated = 0
- engine_control_mutated = 0

----------------
Le laboratoire couvre actuellement 16 scénarios.

MOTEUR / DONNÉES

   attendu : LEGACY

2. autorisation V24 absente
   attendu : LEGACY

3. seulement 3 modèles météo
   attendu : guard BLOCKED / model_count

   attendu : guard BLOCKED / scene24_error_free

ASSETS
5. master officiel absent avant cutover
   attendu : guard BLOCKED / master_asset

SURFACES PUBLIQUES

   attendu : fallback Legacy

7. manifest/fingerprint altéré après écriture
   attendu : fallback Legacy

8. backup Legacy D1 indisponible mais snapshot inline valide
   attendu : Legacy INLINE_BACKUP

9. backup D1 + snapshot inline absents
   attendu : UNAVAILABLE / HTTP 503 sûr
   et surtout JAMAIS V24 non vérifié

STOCKAGE / RÉCUPÉRATION

    attendu : RECOVER_LEGACY

    attendu : RETAIN_PREVIOUS_FORECAST

    attendu : SAFE_503

POINT IMPORTANT
---------------
Les scénarios 10 à 16 ne testent pas une copie théorique de la logique.

Le Bloc 12.8 extrait la politique dans :
src/engine/publicationRecoveryPolicy.ts

ET le vrai code de :
src/storage/publicationSafety.ts

utilise désormais cette même politique.

Le laboratoire vérifie donc la même machine de décision que la production.

PUBLIC FAIL-SAFE TESTABLE
-------------------------
src/engine/publicFailSafe.ts expose maintenant :

resolvePublicSurfaceWithDependencies()

La production l'utilise avec les vraies dépendances :
- backup D1
- ASSETS Cloudflare

Le laboratoire lui injecte des dépendances contrôlées :
- backup absent
- master absent
- etc.

Cela permet de tester les réactions réelles du resolver sans altérer D1.

NOUVEAU BOUTON MOBILE
---------------------
Admin :
"Tester pannes 12.8"

Le bouton lance :
POST /api/admin/fault-lab/run?city=tarnos

Résultat attendu :
PASS

Un résultat PENDING est possible uniquement si la génération courante ne
permet pas de construire un fixture V24 synthétique à partir de scene24 /
DayProfile. Dans ce cas aucune donnée n'est inventée.

FAIL signifie qu'une règle de sécurité attendue n'a pas réagi comme prévu.

SÉCURITÉ
--------
Le laboratoire ne fait jamais :
saveForecast()
rollbackToLegacy()
requestV24Preview()
prepare/confirm V24 approval()

La seule écriture volontaire est :
fault_injection_audit

Le test ne peut donc ni activer V24 ni modifier la météo officielle.

INSTALLATION MOBILE
-------------------
1. Appliquer migrations/0008_fault_injection_audit.sql dans D1.
2. Ajouter/remplacer les fichiers.
3. Déployer.
4. Générer une météo normale si nécessaire.
5. /admin
6. Tester pannes 12.8.
