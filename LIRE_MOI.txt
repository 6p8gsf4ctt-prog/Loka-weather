LOKA V24 — BLOC 12.2
======================

OBJECTIF
--------
Installer la vraie procédure d'AUTORISATION ADMINISTRATIVE V24 :
- readiness obligatoire
- double confirmation
- snapshot immuable
- challenge expirant
- audit append-only

IMPORTANT
---------
Bloc 12.2 N'ACTIVE TOUJOURS PAS V24 officiellement.

Même après une autorisation réussie :
effectiveProduction = LEGACY
productionActivationLocked = true

L'autorisation prépare seulement l'étape technique suivante.

FICHIERS
--------
AJOUTER
- migrations/0004_engine_activation_audit.sql
- src/storage/engineApproval.ts

REMPLACER
- src/engine/engineMode.ts
- src/index.ts
- src/ui/dashboard.ts

Le ZIP inclut aussi les fichiers Bloc 12.1 nécessaires à la cohérence.

MIGRATION D1
------------
0004 crée :
1. engine_approval_challenge
2. engine_activation_audit

engine_activation_audit est APPEND-ONLY :
deux triggers D1 interdisent UPDATE et DELETE.

DOUBLE CONFIRMATION
-------------------
Étape 1 :
POST /api/admin/engine/approval/prepare

Le serveur exige :
readiness.status = READY_CANDIDATE

Si LOKA est NOT_READY ou OBSERVATION :
- HTTP 423
- aucune approbation
- PREPARE_REFUSED ajouté dans l'audit

Si READY_CANDIDATE :
- snapshot readiness + forecast V24
- SHA-256 du snapshot
- challenge de 10 minutes
- événement PREPARED

Étape 2 :
POST /api/admin/engine/approval/confirm

L'Admin doit recopier exactement :
ACTIVER V24 TARNOS

Avant d'accepter, le serveur revérifie :
- challenge encore PENDING
- challenge non expiré
- phrase exacte
- readiness toujours READY_CANDIDATE
- snapshot/fingerprint STRICTEMENT identique
- forecast V24 identique

Si l'historique ou la génération change entre les deux confirmations :
le challenge est annulé et il faut recommencer.

APRÈS CONFIRMATION RÉUSSIE
--------------------------
engine_control devient :
requested_mode = V24
v24_approved = 1
approved_at = ...
approved_by = admin_double_confirmation

MAIS engineMode 12.2 retourne encore :
effectiveProduction = LEGACY
reason = v24_authorized_waiting_activation_bloc_12_3

Donc aucune publication V24 n'est possible dans ce bloc.

ROUTES
------
GET  /api/admin/engine/approval
POST /api/admin/engine/approval/prepare
POST /api/admin/engine/approval/confirm

L'ancienne route :
POST /api/admin/engine/request-v24
ne modifie plus rien et renvoie :
use_double_confirmation_flow

ROLLBACK
--------
Le rollback reste prioritaire et indépendant.

Après rollback réussi :
- requested_mode = LEGACY
- v24_approved = 0
- challenges PENDING annulés
- événement ROLLBACK ajouté à l'audit si possible

Si l'audit D1 échoue, le rollback RESTE réussi.

TEST MOBILE AUJOURD'HUI
-----------------------
Comme readiness = NOT_READY :

1. Appliquer migration 0004 sur D1 distant.
2. Déployer.
3. /admin > Contrôler le moteur.
4. Dans "Autorisation V24 — double confirmation" :
   readiness actuel = NOT_READY
   production effective = LEGACY
5. Appuyer "Préparer l'autorisation V24".
6. Résultat attendu :
   autorisation refusée / readiness_not_ready
7. Recharger "Contrôler le moteur".
8. Dans AUDIT RÉCENT :
   PREPARE_REFUSED
   readiness NOT_READY
9. Production doit rester LEGACY.
10. V24 approuvé doit rester NON.

TEST FUTUR QUAND READY_CANDIDATE
--------------------------------
1. Préparer autorisation.
2. Un challenge de 10 minutes apparaît.
3. Recopier ACTIVER V24 TARNOS.
4. Confirmer.
5. V24 approuvé = OUI.
6. requested_mode = V24.
7. Production effective = TOUJOURS LEGACY.
8. Raison :
   v24_authorized_waiting_activation_bloc_12_3

C'est seulement le Bloc 12.3+ qui pourra utiliser cette autorisation pour
préparer une vraie activation de génération avec rollback automatique.
